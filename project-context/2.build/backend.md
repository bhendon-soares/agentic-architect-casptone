# Backend P0: leituras admin locais

## P1 Aba IA: contrato para @frontend.eng e @integration.eng (2026-10-19)

Todos os quatro GETs `/api/ia-tab/summary`, `/api/ia-tab/details`, `/api/ia-tab/timeseries`, `/api/ia-tab/pricing-config` exigem cliente loopback (o proxy frontend tambem deve permanecer local). Envelope inalterado: `{data: ..., error: null, meta: {request_id: UUID, agent_run_id: null}}`; erro `{data: null, error: {code, message, retryable: false, details: null}, meta: {request_id, agent_run_id: null}}`. Rejeicao local: 403 `ADMIN_LOCAL_ONLY`; parametro invalido: 422 `INVALID_REQUEST`. Sem autenticacao publica.

Os primeiros tres GETs aceitam exatamente `start` e `end` (ISO 8601 com offset obrigatorio, UTC recomendado, `start` inclusivo e `end` exclusivo, filtrados por `agent_runs.started_at`), `model` (string exata do modelo **efetivamente confirmado** por etapa), `step` (`triage|knowledge|response|policy|ticketing`) e `result` (`respond|open_ticket|blocked|ask_clarification|failed|running`). Valores omitidos nao filtram; `start >= end`, data sem timezone ou enumeracao invalida retornam 422. Filtrar por modelo/etapa exclui runs sem telemetria correspondente. Resultado filtra runs antes da agregacao; etapa/modelo selecionam linhas e runs associados. `outcome_unknown` e falha inconclusiva, nao ticket confirmado.

- `summary.data`: `{total_runs: int, telemetry_rows: int, results: {respond|open_ticket|blocked|ask_clarification|failed|running: {count: int, percentage: number|null}}, terminal_denominator: int, duration: {sample_size: int, average_ms: number|null, max_ms: number|null, p95_ms: number|null, p95_method: "nearest-rank"}, estimated_cost_value: number|null, estimated_cost_currency: "USD"|null, cost_sample_size: int, cost_required_rows: int, period: {start: ISO|null, end: ISO|null}, duration_unit: "ms"}`. `percentage` so existe para as tres classes terminais e so quando `terminal_denominator > 0`; inconclusos sempre null. Custo total exige cobertura de **todas** as etapas selecionadas e ao menos uma etapa; amostra/cobertura aparecem mesmo quando o total e null. `total_runs=0` indica ausencia de runs; `total_runs>0, telemetry_rows=0` indica historico/bloqueio sem medicao de etapa.
- `details` aceita adicionalmente `limit` (1..100, padrao 20), `offset` (>=0, padrao 0); `data:{items: [...], total:int}` (total antes da paginacao), `meta.limit`, `meta.offset`. Ordem por inicio de run decrescente, run ID e indice da etapa. Item: `{agent_run_id, session_id, original_run_id, result, step_index, step_name, model_used, deployment_id, start_time, end_time, duration_ms, tokens_input, tokens_output, tokens_cache, estimated_cost_value, estimated_cost_currency, estimated_cost_validity_start, estimated_cost_validity_end, pricing_config_ids, attempt_count, retry_count, replay_count, state}`. IDs e nomes de etapa, modelo, deployment, timestamps, duracao, tokens, custo, moeda e vigencias podem ser `null`. `pricing_config_ids` e sempre lista (vazia quando indisponivel). `attempt_count` e `null` sem transporte instrumentado; `retry_count` e `replay_count` sao inteiros observados (zero se nenhum registro). `state=complete|running|failed`; bloqueios pre-crew e registros historicos retornam linha com etapa nula e consumo nulo. `start_time/end_time` dizem respeito a etapa, nunca ao run total. Para abrir o detalhe da conversa use `session_id` em `/api/admin/conversations/{session_id}` e `agent_run_id` em `/api/agent-runs/{agent_run_id}`.
- `timeseries.data`: `{granularity:"day", days:[{date:"YYYY-MM-DD", results:{respond:int,open_ticket:int,blocked:int,ask_clarification:int,failed:int,running:int}}], states:{...mesmas seis contagens}, stage_latency:{triage|knowledge|response|policy|ticketing:{sample_size,average_ms,max_ms,p95_ms,p95_method}}, duration_unit:"ms", period:{start:ISO|null,end:ISO|null}}`. Datas dos buckets sao UTC; duracoes somente de etapas encerradas, p95 nearest-rank.
- `pricing-config.data`: `{items:[{pricing_config_id,model,deployment_id,currency,token_type,rate_per_million,valid_from,valid_until}],reference_prices:[{model,deployment_id:null,currency:"USD",token_type,rate_per_million,valid_from:null,valid_until:null,active:false}]}`. `items` retorna somente linhas `active=true`; lista vazia significa nenhuma tarifa ativa, e **nao** preco zero. `reference_prices` lista os precos informados de GPT-6 Sol (entrada 2,00; cache 0,20; escrita de cache 2,50; saida 10,00 por milhao), sem deployment ou vigencia comprovados. Nao ha endpoint publico de escrita de tarifas.

Medicao P1: cada `stage()` registra UTC de inicio/fim e `duration_ms` por `perf_counter` do `kickoff()` ate validacao/falha; running nao tem duracao final. Modelo, tokens e tentativas reais continuam `null` no CrewAI atual: `CrewOutput` normalizado, eventos logicos e `successful_requests` nao comprovam consumo nem envios reais do provider. Os precos informados sao visiveis como referencia, nao ativados como tarifa; SKU, regiao, aplicabilidade e vigencia Azure pendentes. Tarifa so e estimada quando modelo/deployment exatos, tokens confiaveis (inclusive cache conhecido), relacao cache-subconjunto e linhas USD ativas sem ambiguidade estiverem presentes na data da etapa; custos nao sao fatura. Configuracoes sobrepostas tornam a estimativa indisponivel. Replays reutilizam o run original, sem novos tokens ou execucoes; retries operacionais sao novos runs com `original_run_id`, sem inferir tentativas de provider. Nao persistimos prompt, resposta bruta, credenciais ou PII nessas tabelas.

Audit P1: `AAMAD_TARGET_RUNTIME=crewai`; migrations novas sem seed de preco. O frontend deve exibir "nao disponivel" para cada campo null, nunca converter null para zero.

## Contratos HTTP

Envelope de sucesso: `{ "data": ..., "error": null, "meta": { "request_id": "UUID", "agent_run_id": null } }`. Erros usam o envelope da API (`data:null`, `error.code`, `meta.request_id`): 422 `INVALID_REQUEST` para paginacao invalida, 422 `INVALID_ID` para UUID invalido, 404 `SESSION_NOT_FOUND` e 403 `ADMIN_LOCAL_ONLY` para cliente nao local.

- `GET /api/admin/conversations?limit=20&offset=0`: `limit` de 1 a 100, `offset` >= 0; `data:{items:[...],total:int}` e `meta.limit/offset`. Cada item tem `session_id`, `status`, `created_at`, `updated_at`, `last_activity_at` e `last_run:{final_action,run_status,error_code}|null`. Atividade inclui atualizacao da sessao, mensagens, inicio/fim de runs e atualizacao de tickets. Ordem decrescente de atividade; desempate por `session_id` crescente. Inclui sessoes sem ticket e nao depende do navegador. `last_run` seleciona maior `started_at` (desempate por `agent_run_id` decrescente). Total conta todas as sessoes antes da paginacao.
- `GET /api/admin/conversations/{session_id}`: `data:{session_id,status,created_at,updated_at,clarification_count,messages,runs,tickets}`. Mensagens: `message_id,agent_run_id,role,message_pt_br,created_at`. Runs (todos, inclusive falhos e sem resposta): `agent_run_id,status,started_at,finished_at,final_action,error_code,summary,sources`. `summary=null` e `sources=[]` quando nao houve resposta. Cada fonte tem somente `title,path,snippet`. Tickets associados: `ticket_id,agent_run_id,status,error_code,servicenow_number,created_at,updated_at`. Mensagens, runs e tickets em ordem cronologica com desempate por ID. Campos de texto sao redigidos na leitura; nao ha `response_data` integral, prompts, payload de incidente, configuracao do modelo ou chain-of-thought.
- `GET /api/agent-runs/{agent_run_id}` continua sendo o detalhe dos eventos redigidos por execucao; `GET /api/chat/sessions/{session_id}` e os contratos de chat/ticket nao mudam.
- `GET /api/metrics/summary`: `responses_with_source` conta apenas runs `completed` com `final_action=respond` e `response_data.sources` nao vazio; as demais metricas mantem a semantica anterior.

IDs sao UUID string; datas nos novos endpoints sao UTC ISO 8601 (offset `+00:00`), valores opcionais usam `null`. As consultas de listagem fazem agregacao e classificacao em SQL, com numero fixo de queries por pagina.

## Limite de exposicao

Os novos endpoints admin so aceitam IP de cliente loopback; `testclient` e reservado para o transporte de testes. Nao existe autenticacao/RBAC P0. Inicie o backend em `127.0.0.1`, mantenha o proxy de desenvolvimento apenas local e nao publique o proxy nem encaminhe estes endpoints via proxy externo: um proxy local pode fazer uma requisicao remota parecer loopback. A protecao local nao substitui autenticacao para deploy publico.

## Validacao P0 do fluxo de agentes e incidente (2026-10-15)

- Runtime resolvido: `crewai`. A regra de confianca e aplicada pelo backend: abaixo de 0.70 pede esclarecimento no primeiro turno; apos uma pergunta abre ticket somente com dados minimos seguros. O endpoint aceita esse ticket apos a pergunta, preservando o envelope HTTP e as validacoes do payload. O limiar exato de 0.70, o bloqueio por veto de QA, dados minimos ausentes e falhas de estagio/timeout simuladas tem testes focados. Texto vetado nunca e devolvido; `risk_flags` e `missing_required_fields` gerados pelo modelo sao redigidos antes de reutilizacao, persistencia ou retorno.
- Provider configurado, teste opt-in com relatos sinteticos: quatro tasks reais em ordem `triage -> knowledge -> response -> policy`, com eventos `validated` individuais e schemas; primeiro relato resultou em `ask_clarification`, segundo em `open_ticket` e validou tambem `ticketing`. Em ambos `sources=[]`: selecao de fonte aplicavel e uma lacuna observada, nao um aceite do fluxo com fonte. Nenhum POST ServiceNow foi feito nesses testes de CrewAI.
- Guardrails locais: fonte so pode ser retornada se aprovada, com hash/categoria compativeis e path elegivel; resposta `respond` exige fonte, e ticket exige correspondencia de impacto, urgencia e categoria. Testes simulados verificam a ordem, configuracao `Process.sequential`, sem delegacao ou memoria, `max_iter=12`, `max_execution_time=60s`, `LLM timeout=30s`, `max_rpm=10` e tratamento de limite invalido. Os ensaios reais nao atingiram timeout nem demonstraram empiricamente imposicao de rate limit ou limite de iteracoes.
- Gate ServiceNow: operador autorizou um unico POST com dados sinteticos e configuracao presente no ambiente. O adapter enviou somente cinco campos (`short_description`, `description`, `impact`, `urgency`, `category`) apos OAuth; confirmou `INC0010004` / `e62afe4c47c0971002d7d48f016d43a8` por GET remoto. Este gate e do adapter, nao de persistencia de ticket via API. Nenhum POST adicional deve ser executado com essa evidencia; falha de resultado incerto nao admite retry automatico.
- Segredos/PII: entrada, fontes, texto da resposta, triagem livre e payload de ticket passam pelo redigimento do backend; eventos de falha guardam apenas codigos estaticos. Testes com sentinelas sinteticas cobrem esses limites e excecoes, mas nao constituem auditoria completa dos logs internos do SDK/provider nem certificacao de seguranca.
- Pendente de decisao conjunta `@product-mgr` e `@integration.eng`: contrato apos esclarecimento quando ainda faltam dados minimos. Atualmente o fluxo interrompe antes da task de ticket e o handler generico existente retorna `AGENT_OUTPUT_INVALID` (502); nao foi definido um novo contrato nem declarado aceite desse caso. Nenhum aceite de `@qa.eng` ou `@security.eng` foi emitido.
